ER YUAN SPACE · DATA HUB

关于 / 设计原理与开发总纲

二元空间 Data Hub 是企业 Context Plane。它先让散落的文件、业务数据、会议结论、产品知识和 AI 产物变成有 ID、负责人、状态、版本、权限和来源的资产，再让人和 Agent 在同一套可信上下文里工作。

一句话定义
先发现事实、整理事实、确认事实，再把正确的事实，在正确的时间，以正确的权限，交给正确的人和 Agent。

01 / WHY

为什么企业需要它

企业的问题通常不是“没有数据”，而是数据一多就开始失控。资料散落在本地电脑、飞书、会议纪要、ERP / CRM、产品文档、研发资料和 AI 会话里。真正缺少的是一套机制，让这些内容能够被统一识别、确认、授权、追踪和使用。

01

版本失控

同一份资料有多个版本，没人知道哪一份是正式版本，哪一份只是讨论稿。

02

责任不清

资料存在，但缺少 Owner，没人负责持续维护、更新、审核和归档。

03

AI 不可信

AI 能搜到内容，却不知道内容是否过期、未审核、重复、敏感或无权限。

04

来源不可追

答案看起来合理，却无法追溯到底依据哪一份文件、哪一段原文、哪一个版本。

05

权限不稳定

敏感内容可能被错误授权给成员、系统或 Agent，造成业务和合规风险。

06

变化不可感知

文件被修改或删除后，没人知道哪些索引、答案、Agent 和业务流程受到影响。

设计判断：第一步不是“让 AI 搜更多资料”，而是先让企业知道自己到底拥有哪些可信资产。
02 / BEYOND RAG

不只是做一个更大的 RAG

传统知识库解决“怎么让模型找到内容”。企业级系统还要解决“这份内容到底能不能被使用”。

普通 RAG 链路
上传文件→Chunk→Embedding→检索→LLM 回答
企业级补充层
身份 / 权限业务线版本审核状态Owner来源引用审计日志
ASSET REGISTRY

从这一刻开始，一份文件不再只是文件，而成为可以被识别、追踪、授权、审核和使用的企业资产。

04 / METHOD

这套方法从哪里来

这不是从零创造的新概念，而是把企业 IT、数据治理和 Agent 时代已经验证的方法，重新组合成适合二元空间第一阶段落地的小闭环。

数据分层

借鉴 Lakehouse / Medallion，把原始事实、处理结果、正式知识和 AI 产物分开。

企业内容管理

借鉴 ECM / DAM / SharePoint / Confluence，让资料拥有 ID、版本、负责人、权限和生命周期。

元数据治理

借鉴 DataHub、OpenMetadata、Purview，建立企业资产总账和目录视图。

RAG 检索

继续使用 Chunk、Embedding、向量 / 关键词 / Rerank，但增加企业级过滤条件。

Agent Context

Agent 不直接拥有所有数据，只能通过受控工具和 API 访问上下文。

Ontology / 图谱

从“哪篇文档写了什么”，走向“企业里的客户、项目、产品、决策之间是什么关系”。

05 / LIFECYCLE

一份资料进入系统以后发生什么

Raw原始资料进入系统，保留来源、上传人、时间和 checksum。
Parsed完成 PDF、Word、Excel、图片、音频等内容解析。
Cleaned去噪、结构化、标题识别、表格抽取、格式整理。
Reviewed人工检查内容、标签、业务归属、负责人和权限。
Approved企业正式确认可以作为正式知识使用。
Indexed完成向量索引、全文索引，已经具备“被找到”的能力。
Serving正式开放给 Agent、企业搜索或业务应用使用。
Archived过期、废弃或归档，不再作为当前上下文提供。
关键拆分：Approved、Indexed、Serving 被刻意拆开，因为“已经审核”“已经索引”“允许 AI 使用”是三件不同的事。
06 / SOURCE OF TRUTH

为什么原始资料必须独立保存

原始资料是 Source of Truth；RAG、向量库、索引和摘要都是可重新生成的派生层。

可以重建：RAGFlow、向量库、Embedding、Chunk、搜索引擎、LLM。
不能丢：原始资料、asset_id、版本、负责人、来源、权限、审核记录。
索引只是派生物：它可以删除、换模型、重新切片、重新生成。
避免供应商绑死：模型和工具可以替换，资产身份不能消失。
07 / VALUE

对人和 AI 分别有什么价值

普通员工

从“翻群、问人、找文件、对版本”，变成直接搜索或提问，并看到来源、版本和更新时间。

业务负责人

知道自己负责哪些资产、哪些待审核、哪些过期、哪些正被 Agent 使用。

管理员

看到资产总量、失败任务、权限异常、重复资产、未分类资料和索引异常。

Agent

看到有身份、状态、版本、权限、来源和关系的资产，而不是一堆无法判断可信度的文档。

过去是“找资料”。未来是：问企业。
08 / AI PIPELINE

AI 的回答链路必须改变

AI 的工作方式从“根据我能搜到的内容回答”，变成“根据当前用户有权访问、企业已经确认、仍然有效的正式资产回答”。

用户问题 ↓ 身份 / 权限检查 ↓ 状态 / 版本过滤 ↓ 向量 + 关键词 + 结构化检索 ↓ Rerank ↓ LLM 根据正式资产回答 ↓ 返回 answer + citations + asset_id
search_assets()
先查权限和状态，再检索。
read_asset()
读取原文、摘要、版本和来源。
generate_report()
产物先进入待审区，不直接覆盖事实。
09 / EVALUATION

我们如何判断它是不是有效

不使用“感觉 AI 回答得不错”作为验收标准，而是用真实业务问题持续评估。第一版先用 20 个妆舟模拟资产和一组真实问题跑通基线。

指标回答什么问题第一阶段目标状态
Retrieval Recall正确资料有没有被检索出来。Top5 ≥ 90%待验收
Citation Accuracy引用来源是否真的支持结论。100%待验收
Freshness是否优先使用最新有效版本。不引用 Deprecated待验收
Permission Accuracy是否严格遵守用户和 Agent 权限。0 次越权待验收
Groundedness回答是否脱离正式资料自由发挥。有据可查待验收
Traceability能否追溯 asset_id、版本和更新时间。100%待验收
图表 / 指标口径：以上是 Phase 1-4 验收目标，不是生产实测结果。当前证据等级为本地功能验证：NocoBase + PostgreSQL 已部署；RAGFlow 已完成本地上传、解析、索引和问答试验。

11 / MVP BOUNDARY

第一阶段刻意不做什么

第一阶段不是建设“大而全数据中台”，而是验证一条最重要的链路：企业真实资料能否稳定变成可信资产，并被 Agent 安全、准确地使用。

不接全公司所有数据源。
不做完整数据仓库和复杂 BI。
不做字段级复杂权限和复杂审批流。
不做第一版自动知识图谱。
不训练垂直模型。
不允许 Agent 直接修改核心业务数据库。
12 / NORTH STAR

最终形态

企业数据 ↓ 统一 Asset ID / 来源 / 负责人 ↓ 统一状态 / 版本 / 权限 ↓ 统一生命周期 / 检索 / Agent Context ↓ 统一审计 / 反馈 / 图谱
我们不会为了 AI 重新创造企业事实。我们负责的是：发现事实、整理事实、确认事实、管理事实，然后把正确的事实，在正确的时间，以正确的权限，交给正确的人和 Agent。
