# 二元空间 DataHub · 正式功能开发路线图

> 版本：v1.0  
> 日期：2026-09-23  
> 目标：从“可演示底座”进入“可使用的企业数据资产 / Context Plane MVP”。  
> 关键结论：第一优先级不是继续美化页面，也不是马上把 RAGFlow 复杂化，而是先建立 **Asset Registry + 状态机 + 权限 + 审计**，让每一份资料都有身份。

---

## 1. 总体判断

上一阶段已经完成：

- NocoBase + PostgreSQL 本地底座。
- RAGFlow 本地上传、解析、索引、问答链路验证。
- “关于 / 设计原理与开发总纲”页面。
- 妆舟 20 个模拟知识包。
- 系统拓扑、处理流程、组件路线和验收口径。

当前问题是这些能力还没有变成一个正式系统。  
所以下一阶段的目标是：

```text
把资料变成资产
把资产变成可审核的知识
把知识变成受控索引
把索引变成可引用的问答能力
把 Agent 变成有权限边界的消费方
```

第一版不追求“大而全数据中台”，只做一个稳定闭环。

## 2. 目标架构

### 2.1 系统分层

```text
NocoBase Console
  资产列表 / 上传 / 审核 / 状态 / 权限 / 任务看板
        ↓
Core API
  Asset Registry API
  File API
  Workflow API
  Search API
  Agent Context API
        ↓
PostgreSQL
  资产账本 / 版本 / 状态 / 标签 / 审核记录 / 审计日志
        ↓
MinIO / OSS / COS
  原始文件 / 处理文件 / 导出文件 / Agent 输出
        ↓
Worker
  解析 / 清洗 / 切分 / Embedding / 同步索引
        ↓
RAGFlow / 向量库 / 全文检索
  检索能力层，不作为唯一事实来源
```

### 2.2 组件边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| NocoBase | 控制台、表单、页面、角色、流程入口 | 不作为唯一业务逻辑中心 |
| Core API | 资产、状态、权限、检索、Agent Context | 不直接做复杂 UI |
| PostgreSQL | 唯一资产账本 | 不保存大文件本体 |
| MinIO / OSS | 文件中心 | 不负责业务状态判断 |
| Worker | 解析、清洗、索引 | 不绕过资产状态 |
| RAGFlow | 解析 / 切分 / 检索适配器 | 不作为唯一事实来源 |
| Agent | 消费上下文 | 不直连数据库，不直接修改业务库 |

## 4. 资产状态机

### 4.1 主状态

```text
Raw
 ↓
Parsed
 ↓
Cleaned
 ↓
Reviewed
 ↓
Approved
 ↓
Indexed
 ↓
Serving
 ↓
Deprecated / Archived
```

### 4.2 状态含义

| 状态 | 含义 | 是否可入索引 |
|---|---|---|
| `raw` | 原始资料刚上传 | 否 |
| `parsed` | 已解析 / OCR / 转文本 | 否 |
| `cleaned` | 已清洗、结构化 | 否 |
| `reviewed` | 人工检查通过，但尚未最终确认 | 可选 |
| `approved` | 正式确认可作为企业知识 | 是 |
| `indexed` | 已完成向量 / 全文索引 | 是 |
| `serving` | 正在给搜索 / Agent 使用 | 是 |
| `deprecated` | 已过时，不再推荐 | 否 |
| `archived` | 已归档 | 否 |

关键原则：

```text
只有 Approved 后的资产才能进入索引。
只有 Indexed 后的资产才能给搜索或 Agent 使用。
所有状态变化必须写 audit_logs。
```

### Phase 3：审核中心

目标：人工确认哪些资料可以进入知识库。

#### 工作项

1. NocoBase 审核中心页面：

```text
待审核
已通过
已驳回
已过期
需要补标签
需要补 Owner
```

2. 审核动作：

```text
approve
reject
request_change
mark_deprecated
archive
```

3. 审核时必须检查：

```text
标题是否准确
内容是否完整
业务线是否正确
标签是否足够
Owner 是否明确
权限范围是否合理
是否存在重复资产
是否包含敏感信息
```

4. 通过后状态进入 `approved`。

#### 验收标准

- 没有 Owner 或标签的资产不能进入 `approved`。
- 每次 approve / reject 都有审核记录。
- 审核通过后资产才能被索引任务消费。
- 被驳回资产不会出现在索引输入列表。

### Phase 4：索引与检索

目标：Approved 资产可被安全检索。

#### 工作项

1. 建索引适配器：

```text
IndexAdapter
  - RagflowAdapter
  - PgVectorAdapter
  - MeilisearchAdapter
```

第一版优先接 RAGFlow，但如果 RAGFlow 太重，可以先用 PostgreSQL + pgvector 做最小索引。

2. 只同步满足以下条件的资产：

```text
status = approved / indexed / serving
review_status = approved
index_status != failed
deleted_at is null
visibility 允许当前目标范围
```

3. 建立 Search API：

```http
POST /api/v1/search
```

输入：

```json
{
  "query": "妆舟有哪些业务线？",
  "filters": {
    "business_line": "zhuangzhou",
    "asset_type": "document",
    "status": ["approved", "indexed", "serving"]
  },
  "top_k": 10
}
```

输出：

```json
{
  "results": [
    {
      "asset_id": "ZZ-DOC-000001",
      "title": "妆舟核心业务线总览",
      "snippet": "妆舟包含公域内容、渠道分销、私域会员……",
      "score": 0.86,
      "version": "v1",
      "updated_at": "2026-09-23"
    }
  ]
}
```

4. 建立 20 个真实测试问题，例如：

```text
妆舟是做什么的？
妆舟有哪些业务线？
草沐知摇摇水的核心卖点是什么？
哪些功效不能随便说？
内容生产流程是什么？
渠道分销第一版怎么处理订单？
私域发送客户前要注意什么？
库存看板应该有哪些字段？
AI 不能直接做什么？
```

#### 验收标准

- 20 个测试问题中至少 90% 能在 Top5 命中正确资料。
- 搜索结果必须返回 `asset_id`、标题、片段、分数、版本、更新时间。
- 未 Approved 资产不能出现在结果中。
- 无权限资产不能出现在结果中。
- 删除或 Deprecated 资产不再被检索。

## 7. 技术选型建议

### 7.1 Core API

推荐：

```text
Python FastAPI + SQLAlchemy + Alembic
```

理由：

- 后续解析、OCR、Embedding、RAG 生态更适合 Python。
- Alembic 可以管理数据库 migration。
- FastAPI 足够轻，也方便给 Agent 提供 OpenAPI 工具。

备选：

```text
Node.js NestJS + Prisma
```

如果团队以后主要维护 JavaScript，可以换成 NestJS，但第一版不建议为了技术栈统一增加风险。

### 7.2 Worker

推荐：

```text
Celery / RQ / Arq + Redis
```

如果使用 FastAPI，优先考虑：

```text
Arq 或 Celery
```

### 7.3 前台控制台

第一阶段：

```text
NocoBase
```

理由：

- 快速搭页面、表单、角色、筛选器。
- 不需要先写完整前端。
- 可以把精力放在 Asset Registry 和数据链路。

后续：

```text
Next.js + shadcn/ui + TanStack Query + Tremor / ECharts
```

当 NocoBase 无法满足复杂交互、图表、Agent 工作台时再自建门户。

### 7.4 文件存储

本地开发：

```text
MinIO
```

生产建议：

```text
腾讯云 COS / 阿里云 OSS
```

### 7.5 检索

第一阶段：

```text
RAGFlow Adapter
```

如果 RAGFlow 本地资源压力大：

```text
PostgreSQL + pgvector
Meilisearch
```

原则：

```text
不要把 RAGFlow 当唯一事实来源。
索引必须可以通过 asset_id 重建。
```

## 10. 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 本机资源不足 | RAGFlow / 索引不稳定 | 本地先做 Asset Registry，索引迁移服务器 |
| 资料质量差 | 检索不准 | 先做清洗、审核和标签，不直接全量入 RAG |
| 只做演示不接真数据 | 无法验证价值 | 第一周就导入 20 个妆舟资产 |
| RAGFlow 过度耦合 | 后续难替换 | 用 Adapter，不把 RAGFlow 当唯一事实来源 |
| Agent 权限失控 | 合规风险 | Agent 只走 Context API，全部审计 |
| 页面过度开发 | 延误核心链路 | 先做列表、详情、上传、审核、搜索 |
| 没有评估集 | 无法证明有效 | 先建 20 个真实问题集 |
