# DataHub 产品与架构收敛方案

> 版本：v1.0  
> 日期：2026-09-24  
> 状态：执行中  
> 目标：停止功能继续发散，把 NocoBase、DataHub Core、前端、数据、页面和演示入口收敛成一套可交付产品。

---

## 1. 结论

从现在开始，DataHub 采用唯一主架构：

```text
DataHub Web 前端
 ↓
DataHub Core API
 ↓
PostgreSQL
 ↓
对象存储 / 解析 Worker / 索引服务 / 图谱 / Agent
```

NocoBase 不再作为 DataHub 的主产品后端。

NocoBase 只保留两个用途：

1. 过渡期后台管理。
2. 后续可选的低代码配置/运营后台。

用户和客户只使用一个入口：

```text
http://127.0.0.1:13001/
```

生产环境使用：

```text
https://datahub.xxx.com
```

## 2. 当前问题

### 2.1 入口混乱

目前存在多个入口：

```text
http://127.0.0.1:13000
http://127.0.0.1:13000/admin/datahub-console-route
http://127.0.0.1:13001
http://127.0.0.1:13001/datahub-console.html
```

用户不知道哪个是正式入口。

### 2.2 后端职责不清

NocoBase 原来承担：

```text
页面
菜单
资产表
任务表
审核表
API
权限
```

后来为了实现第 1-6 期，又新增了：

```text
DataHub Core API
解析 Worker
文件存储
审核状态机
检索
问答
Agent
图谱
BI
审计
```

结果导致两套后端并存。

### 2.3 数据分裂

目前有两份类似的妆舟模拟资产：

```text
一份在 NocoBase PostgreSQL 中
一份在 DataHub Core SQLite/PostgreSQL 中
```

这会导致：

```text
不知道哪份是最新
不知道哪份是正式
不知道索引读哪边
不知道审核改哪边
```

### 2.4 UI 形态分裂

目前同时存在：

```text
NocoBase 原生页面
NocoBase iframe
自定义 Console
独立静态页
```

导致产品整体感弱。

### 2.5 功能状态不透明

有些功能是可用，有些是演示，有些是接口已经存在但页面没有接入，有些只是占位。


```text

review_logs
index_records

audit_logs
users
entities
relationships
agent_logs
```

### 6.2 NocoBase 原数据处理

NocoBase 中的：

```text
datahubAssets
datahubJobs
datahubReviews
```

不再作为主数据源。

处理方式：

```text
1. 导出旧数据。
2. 与 Core API 数据比对。
3. 按 asset_id / checksum / title 去重。
4. 正式数据导入 PostgreSQL DataHub DB。
5. NocoBase 表保留为历史快照。
```

### 6.3 文件存储

统一目录：

```text
datahub/
  01_raw/
  02_staging/
  03_curated/
  04_index_input/
  05_agent_output/
  90_archive/
```

开发环境使用本地目录。

生产环境使用：

```text
MinIO / OSS / COS
```

### 7.2 第一版暂时隐藏

| 功能 | 原因 |
|---|---|
| 字段级权限 | 复杂度高，暂不进入 MVP |
| 完整数据仓库 | 不属于第一版 |
| 全量数据源同步 | 需要稳定资产层后再做 |
| 自动图谱抽取 | 先人工确认核心关系 |
| 多语言知识库 | 后续扩展 |
| 复杂审批流 | 第一版只做基础审核 |

### 7.3 明确不做

```text
第一版不接全公司所有数据源
第一版不做完整数据仓库
第一版不做大规模 BI
第一版不让 Agent 直接写业务库
第一版不做无审核自动入知识库
```

## 10. 权限模型

### 角色

```text
管理员
业务负责人
审核员
普通成员
Agent
```

### 权限

| 角色 | 权限 |
|---|---|
| 管理员 | 全部 |
| 业务负责人 | 管理本业务线资产 |
| 审核员 | 审核、驳回、归档 |
| 普通成员 | 上传、查看授权资产 |
| Agent | 只能访问授权且 Approved 后资产 |

### Agent 第一阶段只允许

```text
search_assets()
read_asset()
generate_report()
```

### Agent 不允许

```text
直连数据库
修改业务系统
删除资产
访问未授权资产
输出无引用的企业结论
```

## 11. 收敛阶段

### Phase A：冻结功能

```text
1. 冻结新功能。
2. 保留当前 Core API。
3. 隐藏未完成模块。
4. 只修复阻断问题。
```

验收：

```text
有一个明确主入口。
有一个明确后端。
有一个明确数据源。
```

---

### Phase B：数据统一

```text
1. 建立 PostgreSQL DataHub DB。
2. 导出 NocoBase 旧数据。
3. 去重并迁移资产。
4. 迁移文件路径。
5. 建立资产版本和文件关系。
```

验收：

```text
所有正式资产只存在于一个业务库。
每个资产有唯一 asset_id。
每个资产能找到 raw 文件和 processed 文件。
```

---

### Phase C：前端产品壳统一

```text
1. 建立统一侧边栏。
2. 建立统一顶栏。
3. 统一中文文案。
4. 统一组件风格。
5. 隐藏未完成功能。
```

验收：

```text
用户只看到一个入口。
页面不再有中英文混杂。
界面不再有 iframe 割裂感。
```

---

### Phase D：真实文件与解析

```text
1. 接入 MinIO / OSS / COS。
2. 实现上传 presign。
3. 实现真实 Worker。
4. 支持 PDF / DOCX / XLSX / CSV / Markdown。
5. 建立失败重试。
```

验收：

```text
20 个资产解析成功率 ≥ 90%。
失败任务有明确原因。
原始文件不可覆盖。
解析结果可重建。
```

---

### Phase E：索引与问答

```text
1. 接入 pgvector。
2. 接入全文索引。
3. 实现 Hybrid Search。
4. 只索引 Approved 资产。
5. Ask API 返回引用。
```

验收：

```text
20 个问题 Top5 命中率 ≥ 90%。
回答引用覆盖率 100%。
无权限资产出现次数 0。
```

---

### Phase F：图谱、Agent、BI

```text
1. 完成图谱实体关系模型。
2. 接入图谱可视化。
3. 开放 Agent 三个工具。
4. 接入 BI 指标。

```

验收：

```text
Agent 可搜索、读取、生成报告。
图谱能回答关系型问题。
BI 能看到核心指标。
```

## 14. 最终定位

> DataHub 不是网盘，不是普通知识库，也不是 NocoBase 的附属页面。  
> 它是企业的 Context Plane：让资料先变成可信资产，再变成人和 AI 可以安全使用的上下文。

---

## 15. 一句话执行原则

> 先统一入口和数据，再统一体验，再扩展智能能力。  
> 不再让 NocoBase、新前端、新后端各自长出一套东西。
