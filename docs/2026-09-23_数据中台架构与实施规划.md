# 二元空间 Data Hub：企业 Context Plane 架构与实施规划

> 版本：v0.1  
> 日期：2026-09-23  
> 目标：定义企业数据资产层、知识索引层和 Agent 上下文层的最小可落地架构。  
> 一句话定位：**这不是一个传统网盘，也不是单纯 RAG 知识库，而是让企业数据“可登记、可处理、可信任、可检索、可被 Agent 使用”的 Context Plane。**

---

## 1. 我们要解决什么问题

企业资料通常分散在多个地方：

```text
本地电脑
飞书 / 企业微信
RAGFlow
ERP / CRM / U8 / 有赞
会议纪要
产品文档
合同
研发资料
数据库导出
AI 生成结果
```

这些数据常见问题是：

| 问题 | 后果 |
|---|---|
| 没有统一资产 ID | 同一份资料有多份副本，无法判断哪份最新 |
| 没有统一状态 | 不知道哪些是原始资料、哪些是确认后的正式知识 |
| 没有负责人 | 资料无人维护，过期、错误、重复 |
| 没有权限边界 | 敏感资料可能被错误授权给成员或 Agent |
| 没有来源 | AI 回答无法追溯依据 |
| 没有生命周期 | 不知道哪些该归档、哪些该删除、哪些该重新索引 |
| 没有图谱关系 | 无法回答“这个客户关联哪些项目 / 决策 / 产品” |

因此，我们不是要马上做一个“大而全数据中台页面”，而是先建立一个企业级 **Context Plane**。

---

## 2. 核心理念

### 2.1 Context Plane 是什么

Context Plane 是企业数据的上下文层。

它位于业务系统、文件存储、知识索引和 AI Agent 之间：

```text
业务系统 / 文件 / 消息 / Agent 产物
        ↓
原始数据区
        ↓
处理区
        ↓
整理区 / 标签区
        ↓
索引区
        ↓
图谱区
        ↓
Agent / 门户 / 业务应用
```

### 2.2 它要保证每份资产能回答五个问题

每一份数据都应该能回答：

1. **这是什么？**
2. **从哪里来？**
3. **谁负责？**
4. **谁能使用？**
5. **哪些 Agent 或业务正在使用？**

### 2.3 核心原则

```text
原始文件是 Source of Truth。
知识库索引只是派生视图。
Agent 不能绕过权限。
AI 回答必须带来源。
正式资料必须有人审核。
所有关键操作都要留痕。
```

## 4. 数据生命周期

每一份资产都会经历状态流转：

```text
Raw
 ↓
Parsed
 ↓
Cleaned
 ↓
Reviewed
 ↓
Approved
 ↓
Indexed
 ↓
Serving
 ↓
Deprecated / Archived
```

### 状态定义

| 状态 | 含义 | 是否可入知识库 |
|---|---|---|
| `Raw` | 原始资料刚上传 | 否 |
| `Parsed` | 已完成解析 / OCR / 转文本 | 否 |
| `Cleaned` | 已清洗、去噪、结构化 | 否 |
| `Reviewed` | 人工已检查 | 可选 |
| `Approved` | 已确认可作为正式知识 | 是 |
| `Indexed` | 已生成向量 / 全文索引 | 是 |
| `Serving` | 正在给 Agent / 检索使用 | 是 |
| `Deprecated` | 已过时，不再推荐 | 否 |
| `Archived` | 已归档 | 否 |

## 5. 存储分层

不要把所有文件都塞进 RAGFlow 或数据库。

建议按生命周期分区：

```text
datahub/
  01_raw/
  02_staging/
  03_curated/
  04_index_input/
  05_agent_output/
  90_archive/
```

### 5.1 `01_raw/` 原始数据区

存放：

```text
原始 PDF
Word
Excel
图片
音频
视频
系统导出文件
聊天记录导出
```

特点：

- 不轻易修改。
- 保留原始 checksum。
- 记录上传人、来源、时间。
- 是 Source of Truth。

### 5.2 `02_staging/` 处理区

存放：

```text
解析后的 Markdown
OCR 结果
JSON 结构化数据
抽取后的表格
临时摘要
```

特点：

- 可以重新生成。
- 不作为最终可信数据。
- 失败可以删除重跑。

### 5.3 `03_curated/` 整理区

存放：

```text
已清洗产品资料
已确认会议纪要
已审核 SOP
已打标签客户需求
已结构化决策记录
```

特点：

- 人工确认或 AI 生成 + 人工确认。
- 有 Owner。
- 有标签。
- 有状态。
- 可以进入知识库。

### 5.4 `04_index_input/` 索引输入区

存放即将进入 RAG / 搜索索引的数据。

特点：

- 来自 `03_curated/`。
- 状态必须是 `Approved`。
- 可以删除后重建。

### 5.5 `05_agent_output/` Agent 输出区

存放：

```text
Agent 报告
摘要
知识卡片
图谱抽取草稿
方案草稿
```

特点：

- AI 输出先进入这里。
- 人工确认后才能升级为正式资产。
- 不允许直接覆盖原始资料。

| `source_type` | enum | 上传 / API / 同步 / Agent 生成 |
| `source_system` | string | 来源系统 |

| `raw_uri` | string | 原始文件位置 |
| `processed_uri` | string | 解析后文件位置 |
| `owner` | string | 负责人 |
| `tags` | array | 标签 |
| `status` | enum | Raw / Parsed / Cleaned / Reviewed / Approved / Indexed |
| `visibility` | enum | 私有 / 团队 / 公司 |
| `review_status` | enum | 待审核 / 已审核 / 驳回 |
| `index_status` | enum | 未索引 / 索引中 / 已索引 / 失败 |
| `graph_status` | enum | 未生成 / 生成中 / 已生成 |

| `checksum` | string | 文件指纹 |
| `created_by` | string | 创建人 |
| `created_at` | datetime | 创建时间 |
| `updated_by` | string | 更新人 |
| `updated_at` | datetime | 更新时间 |
| `retention_policy` | string | 保留策略 |

## 7. 权限模型

### 7.1 基础角色

| 角色 | 权限 |
|---|---|
| 管理员 | 管理所有资产、用户、配置 |
| 业务负责人 | 管理本业务线资产 |
| 普通成员 | 查看被授权资产 |
| 审核员 | 审核、驳回、标记资料 |
| Agent | 只能访问被授权资产 |

### 7.2 权限检查原则

Agent 每次访问前必须检查：

```text
这个资产是否存在？
这个资产是否 Approved？
这个用户 / Agent 是否有权限？
这个资产是否属于当前企业？
这个资产是否被禁用或归档？
```

### 7.3 Agent 权限原则

Agent 不直接访问数据库。

Agent 只能通过受控 API：

```text
search_assets()
read_asset()
create_asset()
update_asset()
propose_delete_asset()
generate_report()
```

第一阶段只开放：

```text
search_assets()
read_asset()
generate_report()
```

## 8. 技术组件建议

### 8.1 推荐最小组合

| 能力 | 推荐 |
|---|---|
| 控制台 / 页面 | NocoBase，后期可换 Next.js 自建门户 |
| 资产元数据 | PostgreSQL |
| 文件存储 | MinIO / OSS / COS |
| 异步任务 | Celery / RQ / BullMQ / Temporal |
| 文档解析 | Docling / MinerU / Apache Tika / Unstructured |
| OCR | PaddleOCR / RapidOCR |
| 音频转写 | Whisper / faster-whisper |
| 向量检索 | PostgreSQL + pgvector，后期 Qdrant |
| 全文检索 | Meilisearch / OpenSearch |
| LLM | DeepSeek |
| Embedding | BAAI/bge-m3 |
| 图谱 | 第一版 PostgreSQL，后期 Neo4j |
| 可观测 | Langfuse / OpenTelemetry |

### 8.2 RAGFlow 的定位

RAGFlow 可以作为：

```text
文档解析
切片
Embedding 调用
检索
引用回答
```

的能力组件。

但不建议让 RAGFlow 成为：

```text
唯一原始数据存储
企业权限中心
资产生命周期中心
最终门户
数据中台本体
```

更合理的关系是：

```text
NocoBase / Context API 是主控台。
RAGFlow 是知识索引引擎。
MinIO 是文件 Source of Truth。
PostgreSQL 是资产 Source of Truth。
```

## 9. 核心流程

### 9.1 上传流程

```text
用户上传文件
 ↓
写入 MinIO / 文件存储
 ↓
生成 checksum
 ↓
创建 asset_id
 ↓
状态：Raw
 ↓
投递解析任务
```

---

### 9.2 解析流程

```text
读取 raw 文件
 ↓
判断文件类型
 ↓
PDF / Word / 图片 / Excel / Markdown 分发
 ↓
解析为 Markdown / JSON
 ↓
保存到 staging
 ↓
更新状态：Parsed
```

---

### 9.3 清洗流程

```text
读取解析结果
 ↓
去页眉页脚
 ↓
去除无效空行
 ↓
抽取标题
 ↓
识别章节
 ↓
抽取表格
 ↓
生成摘要候选
 ↓
更新状态：Cleaned
```

---

### 9.4 人工审核流程

```text
Cleaned 资产进入审核列表
 ↓
审核人检查标题、内容、标签、权限
 ↓
通过：Reviewed
 ↓
补充业务信息
 ↓
状态：Approved
 ↓
允许进入索引
```

---

### 9.5 索引流程

```text
Approved 资产
 ↓
切片
 ↓
调用 Embedding
 ↓
写入向量库
 ↓
写入全文索引
 ↓
更新状态：Indexed
```

---

### 9.6 检索流程

```text
用户提问
 ↓
权限检查
 ↓
Query 改写
 ↓
向量检索
 ↓
关键词检索
 ↓
结构化过滤
 ↓
Rerank
 ↓
返回 Top K
 ↓
LLM 根据引用生成答案
 ↓
返回答案 + asset_id + 文件名 + 更新时间
```

---

### 9.7 Agent 产出回流

```text
Agent 生成报告 / 摘要 / 方案
 ↓
进入 05_agent_output/
 ↓
人工审核
 ↓
确认后升级为正式资产
 ↓
必要时进入知识库
```

## 10. Context API 设计

第一阶段只需要这些 API。

### 10.1 资产检索

```http
POST /api/v1/assets/search
```

输入：

```json
{
  "query": "妆舟有哪些业务线？",
  "filters": {
    "business_line": "妆舟",
    "status": ["Approved", "Indexed"]
  },
  "top_k": 10
}
```

输出：

```json
{
  "results": [
    {
      "asset_id": "ZZ-DOC-000001",
      "title": "妆舟核心业务线总览",
      "score": 0.86,
      "snippet": "妆舟包含公域内容、渠道分销、私域会员..."

}
```

## 12. 分阶段实施

### Phase 0：明确试点范围

选择一个试点业务，例如：

```text
妆舟
```

第一批资料只放：

```text
产品资料
业务流程
组织分工
会议纪要
风险边界
术语表
测试问题
```

不放：

```text
敏感合同
财务明细
客户个人信息
未确认资料
```

---

### Phase 1：资产登记

目标：

```text
每份资料都有 asset_id。
```

工作：

1. 建 PostgreSQL 资产表。
2. 建 MinIO 存储结构。
3. 手工或批量登记 20 个资产。
4. 每个资产记录来源、负责人、状态、标签。

验收：

```text
能列出所有资产。
能根据 asset_id 查询资产。
能知道资产负责人和状态。
```

---

### Phase 2：解析 Worker

目标：

```text
自动解析常见资料。
```

支持：

```text
Markdown
Word
PDF
CSV
Excel
简单图片 OCR
```

输出：

```text
Markdown
JSON
Chunk
```

验收：

```text
20 个资产中至少 90% 解析成功。
解析结果可读。
失败资产有明确错误。
```

---

### Phase 3：人工审核

目标：

```text
确保进入知识库的资料可信。
```

工作：

1. 建审核页面。
2. 人工检查解析结果。
3. 补充标题、标签、业务线。
4. 状态变为 Approved。

验收：

```text
所有 Approved 资产都有 Owner。
所有 Approved 资产都有标签。
所有 Approved 资产都有审核记录。
```

---

### Phase 4：索引和检索

目标：

```text
Approved 资产可被语义 / 关键词检索。
```

工作：

1. Chunk 切分。
2. Embedding。
3. 写入向量库。
4. 写入全文索引。
5. 提供 search API。

验收：

```text
20 个真实问题能返回相关结果。
结果包含 asset_id 和标题。
无权限资产不会返回。
```

---

### Phase 5：Agent 接入

目标：

```text
Agent 基于授权资料回答。
```

工作：

1. 建 Context API。
2. Agent 通过 API 检索资产。
3. 回答带引用。
4. 记录 Agent 查询日志。

验收：

```text
Agent 不能访问未授权资产。
回答必须带来源。
问答链路稳定。
```

---

### Phase 6：图谱和治理

目标：

```text
建立核心实体关系。
```

工作：

1. 定义实体：业务线、模块、负责人、产品、客户、文档、决策。
2. 定义关系：包含、负责、提出、影响、描述、来源。
3. 人工整理第一版关系。
4. 后续再用 AI 抽取。

验收：

```text
能回答关系型问题：
这个决策来自哪次会议？
这个客户关联哪些项目？
这个产品由谁负责？
```

## 13. 第一版不要做的事

第一阶段明确不做：

```text
1. 不接全公司所有数据源。
2. 不做完整数据仓库。
3. 不做字段级权限。
4. 不做复杂血缘。
5. 不做大规模 BI。
6. 不做自动知识图谱。
7. 不做垂直模型。
8. 不做复杂审批流。
9. 不让 Agent 直接写业务数据库。
10. 不把所有资料无脑塞进 RAG。
```

## 15. MVP 验收标准

第一版完成的判断标准：

1. 每份资料都有唯一 `asset_id`。
2. 能查到资产负责人、来源、状态、标签。
3. 原始文件保存在 `01_raw/`。
4. 解析文件保存在 `02_staging/` 或专门解析区。
5. 只有 `Approved` 资产进入知识库。
6. 知识库状态可见：未索引 / 索引中 / 已索引 / 失败。
7. AI 回答必须带引用。
8. 无权限用户不能检索未授权资产。
9. Agent 不能绕过 Context API。
10. 删除或更新资产后，索引可以同步。
11. 索引可以重建，原始资料不受影响。
12. 20 个真实测试问题中，至少 15 个能命中正确资料。

## 16. 与 RAGFlow 的关系

RAGFlow 可以继续使用，但定位要清楚。

### RAGFlow 适合做

```text
PDF / Word / PPT / Excel 解析
Chunk 切分
Embedding 编排
向量 / 全文检索
引用回答
知识库问答
```

### RAGFlow 不适合作为

```text
唯一原始数据存储
企业权限中心
资产生命周期中心
最终门户
数据中台本体
```

### 正确关系

```text
NocoBase / Context API = 资产控制台
PostgreSQL = 资产账本
MinIO = 文件中心
RAGFlow = 知识索引引擎
DeepSeek = 回答生成
BAAI/bge-m3 = Embedding
```

## 17. 风险与注意事项

### 17.1 不要一开始接全部数据

先选一个业务线 / 项目。

---

### 17.2 不要把敏感资料直接给云模型

客户个人信息、财务数据、合同条款需要先脱敏或单独权限处理。

---

### 17.3 不要让 Agent 直接写业务库

Agent 产物先进入输出区，人工确认后再升级。

---

### 17.4 不要频繁更换 Embedding 模型

Embedding 模型变化通常需要重新向量化。

---

### 17.5 不要只看答案，不看引用

没有引用的答案不能作为企业决策依据。

## 19. 当前建议

### 暂缓

1. 知识图谱。
2. 大规模数据源接入。
3. 复杂权限。
4. BI 看板。
5. 垂直模型。
6. 全公司推广。

## 20. 一句话总结

> 我们要做的不是“一个更大的 RAGFlow”，而是企业级 Context Plane。  
> 先用最小闭环管理资产、权限、状态、来源和检索，  
> 再逐步长出知识图谱、Agent、BI 和完整数据中台。
